# FSR1

Реализация использует официальные EASU и RCAS AMD, FP32, два fragment-прохода.
Исходники зафиксированы на commit `a21ffb8f6c13233ba336352bdff293894c706575`;
уведомления MIT сохранены в `unity/Assets/NxPort/Fsr/Vendor` и в сборке.

`PostProcessV2_Handler` создаёт внутренние RT по `render_height`. Virtual Camera
собирает сцену и HUD в низком разрешении. Отдельная камера вывода выполняет EASU
в 1280×720, затем RCAS на экран. Screen остаётся 1280×720. Масштабируется и HUD.
Это пространственный FSR1: без генерации кадров и временной истории.

В поставляемом config: `fsr 1`, `render_height 540`, `fsr_sharpness 0.5`.
В r32 внутренний рендер поддерживает 180–720p; профиль по умолчанию остаётся 540p. Значение sharpness 0..2: 0 — самая сильная резкость.
`fsr 0` возвращает обычный вывод. Встроенный default загрузчика — fsr=0;
включение в дистрибутиве задаётся config и требует Android shader bundle
`assets/NxPort/nx_fsr.bundle` вместе с актуальным managed-кодом.

Bundle строится через `NxFsrBuild.Export`, после GPU-проверки цветов и ориентации
обоих проходов. На Switch r26 получены `active EASU+RCAS 960x540->1280x720`
и `first output frame` после смены сцены. Ошибка шейдера, потеря RT или неверный
порядок камер включают fallback с причиной в журнале.

Для A/B нужен один маршрут и одинаковые частоты: 540p без FSR, 540p с FSR,
480p с FSR. Сравнивать frame/p95/max, draws, CPU и память. Время SwapBuffers
не равно полной загрузке GPU. FSR не ускоряет игровую логику главного потока.
Прирост FPS этим прогоном ещё не измерен. Все эффекты и сцены требуют проверки.


## Управление через FSR-NX / Ryazha-clk (r32)

Найденный на тестовой карте `SaltySD/plugins/FSR/01005CE3B1A40000.ini`
принадлежит FSR-NX. Его исходный GPU-backend перехватывает NVN, тогда как наш
загрузчик работает через Mesa/GLES. Stock SaltyNX 2.1.3 не содержит этого
пользовательского FSR-backend. В r32 порт сам публикует совместимые блоки
FSR1 v3 (128 байт) и FSRC (24 байта) в общей памяти SaltyNX. Глобальное ядро
и оверлей не подменяются ещё раз; EASU/RCAS выполняются внутри Unity.

В разделе FSR оверлея поддержаны процент рендера, переключатель фильтра и
резкость. Диапазон фактического масштаба — 25–100% от 720p: 50% = 360p,
75% = 540p, 100% = 720p. Выход остаётся 1280×720. Изменения проверяются
раз в 0.25 с и пересоздают RT на границе кадров. Все RT мира/эффектов
по-прежнему принадлежат игровому PostProcessV2_Handler.

Реализован EASU+RCAS. При выключенном фильтре используется bilinear blit.
FSR Lite, NVN/HDR/depth/shader-fix и расширенный FSRE-протокол не реализованы;
неподдержанные FSRC-поля нормализуются к поддержанным значениям. Размер буфера,
номер кадра и applied-ревизия сообщаются после вывода соответствующей композиции.
Это подтверждает подачу команд кадра, а не измерение завершения GPU; gpuTimeUs
остаётся нулём. Произвольные 200%/4K этим интерфейсом не заявляются.

При старте сохранённый INI учитывается, если enabled=1 либо scale отличается
от шаблонных 100%. Шаблон enabled=0/scale=100 сохраняет испытанный профиль
config.txt (540p/FSR1). При отсутствии моста сохраняется управление через config.
Для выключения фильтра на лету пользуйся переключателем FSR в оверлее;
`fsr 0` в config отключает весь компонент после перезапуска.

Журнал: `[fsr-control] ... mapped`, затем `request=... pending render`;
`[fsr] first output ...` подтверждает новый размер композиции. Аппаратная
проверка изменений в оверлее r32 ещё нужна. Шаг физики и часы не меняются.

Получение render_height фиксирует целую ревизию настроек для следующих
чтений sharpness/filter, чтобы отдельные P/Invoke не смешивали две публикации
оверлея. Следующий снимок принимается на следующем чтении render_height.
