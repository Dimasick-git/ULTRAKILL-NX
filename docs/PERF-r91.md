# r91: независимые FPS и частота дисплея

Последний запуск r90: `FPS offset=0`, `reported display refresh=80`, запрос 60
успешен, но повторный read остаётся 80. Блок начинался с magic 0x00465053:
его байт по адресу shared_base+1 равен 0x50 (80). Этот же адрес используется
GetDisplayRefreshRate(..., false) в SaltyNX для чтения кэша частоты дисплея.
Это точная коллизия диапазонов, а не доказательство работы панели на 80 Гц.

Источник протокола: [SaltyNX display_refresh_rate.cpp](https://github.com/masagrator/SaltyNX/blob/master/saltysd_proc/source/display_refresh_rate.cpp),
GetDisplayRefreshRate, чтение shared memory + 1. Сверено также с локальным
снимком service.txt / proc211.txt и ABI 2.1.1.

Исправление:

- Первые четыре байта исключены из поиска и размещения FPS/FSR.
- У первого выделения резервируется дополнительный префикс; payload начинается
  после него. Проверяются границы и выравнивание.
- Старое перекрытие удаляется до публикации нового блока. Значение частоты
  остаётся неизвестным до обновления со стороны sysmodule, вместо подстановки 60.
- Отдельная метка владельца сохраняет корректное повторное подключение, даже
  когда FSR controls находятся отдельно от FPS. Чужой producer остаётся read-only.
- Не вызывается SetDisplayRefreshRate по показанию телеметрии. FPS и refresh
  публикуются раздельно; изменение FPS на 30/144 не записывает эти числа в refresh.

Хостовые тесты компилируют production C с -UNDEBUG: воспроизводят 80 из magic,
миграцию целого и частично обновлённого заголовка, два повторных запуска,
неизменность контрольных байтов, обновление refresh из sysmodule, отсутствие
команд изменения частоты и поддержку всех FPS presets. Это не измерение
аппаратной частоты на Switch; повторная консольная проверка остаётся необходимой.
