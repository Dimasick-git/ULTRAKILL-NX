# Локальная проверка r26

Эта сборка пока не публикуется на GitHub. Подтверждённого прироста FPS на Switch
ещё нет. Сначала нужен журнал с CPU-профилем и A/B одного тяжёлого участка.

## Что изменено

- Сохранена правка r25: `IL2CPP_GC_MODE_ENABLED = 1`, состояние проверяется
  через `il2cpp_gc_is_disabled`. Значение 0 в r23/r24 ошибочно выключало GC.
  Свежий аппаратный журнал r25 показывает `disabled=0`, растущий `stw_passes`
  и managed heap около 80 МБ во время этого прогона.
- `sched_getaffinity` заполняет маску, `sched_setaffinity` применяет её через
  Horizon; raw syscall 122/123 также обслуживаются. Число CPU и /proc,/sys
  берутся из `InfoType_CoreMask`, а не из константы. Запрос недоступного
  ядра не превращается в фиктивный успех.
- `[cpu-perf]` раз в 5 секунд показывает самые активные зарегистрированные
  потоки. 100% — ёмкость одного ядра. Снимки стеков для этого не делаются;
  системные потоки и GPU в эту сумму не входят.
- `dladdr` сообщает имя и базовый адрес загруженной библиотеки. Раньше
  заглушка всегда возвращала 0; это мешало native stack traces IL2CPP.
  Символьное имя для stripped-метода может оставаться пустым — сопоставление
  managed-методов выполняет сам IL2CPP по таблице регистрации.
- Чтение строк PlayerPrefs больше не пишет значения в SD-журнал каждый кадр.
  Поведение самих чтений и журнал исключений сохранены.
- Первые восемь неудачных shader link сохраняют исходники прикреплённых
  стадий в `shader-errors/`. Ошибки не подавляются, материалы не подменяются.

## FSR

Реальные EASU и RCAS из зафиксированной версии AMD, два fragment-прохода FP32.
Без генерации кадров, depth/motion history и CPU-масштабирования пикселей.
Шейдеры поставляются отдельным Android-бандлом `assets/NxPort/nx_fsr.bundle`.

Порядок: игровой `PostProcessV2_Handler` задаёт пониженный размер мира/глубины,
его Virtual Camera собирает картинку в пониженный RT; пустая камера вывода
выполняет EASU в 720p и RCAS в экран. Unity Screen остаётся 1280×720, второго
увеличения с 540p Screen нет. Первая версия включает HUD в исходный RT,
поэтому HUD также масштабируется. Нативный HUD после FSR — отдельная задача.

`fsr 1` включает FSR, `fsr 0` возвращает прежнюю схему.
`render_height 540` или `480` задаёт высоту исходного RT; 360 также поддержана.
`fsr_sharpness 0.5`: диапазон 0..2, 0 — самая сильная резкость RCAS.
В обычном профиле fsr по умолчанию 0; включение требует полного комплекта r26.
Не сочетать `fsr 1` и `render_height 720`: нужен меньший исходный размер.
При неподдерживаемом шейдере, потерянном RT, неправильном порядке камер или
смене разрешения включается fallback с объяснением в журнале.

На ПК через OpenGL ES 3 проверены два настоящих GPU-прохода, цвета и
ориентация тестовых квадрантов. Собран Android-бандл, Unity export без ошибок.
Эти проверки не подтверждают совместимость порядка камер каждой сцены на Switch.

## Как сравнить

Стабильные одинаковые частоты и тайминги RAM; один уровень, маршрут и настройки.
Сначала 540p с `fsr 0`, затем 540p с `fsr 1`: это измерит цену фильтра.
После этого 480p с `fsr 1`: меньше пикселей может помочь GPU-нагрузке.
Сравнить средний/p95/max кадра, CPU-потоки, число draw calls и память.
Не считать CPU-время SwapBuffers измерением всей GPU-работы.

В журнале FSR нужны обе строки: `active EASU+RCAS` и `first output frame`.
Если появился fallback, FSR в этом прогоне не работает, независимо от настройки.
Проверить меню A/B, HUD, видео, порталы, воду, переходы и повторную загрузку.

Четвёртое ядро нельзя получить изменением возвращаемого CPU count: наш форвардер
разрешает ядра 0–2. Новая диагностика покажет реальную маску процесса; форвардер
и системные права этой сборкой не расширяются.

## Сбой при таймингах RAM

В отчёте r24 PC попал в `Door.Update` на изменённую инструкцию: ожидаемая
`0x6d4423e9`, зарегистрированная ядром `0x7f4423e9`. Библиотека на SD имела
правильный SHA-256. На снимке RAM 1996,8 МГц; пользователь подтвердил
эксперимент с таймингами и сообщил об исчезновении сбоя после возврата.
Это отдельное наблюдение от ошибки режима GC. Долгий тест стабильности нужен.
