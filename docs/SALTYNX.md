# SaltyNX для загрузчика NRO

На тестовую карту записан официальный SaltyNX 2.1.3; прежняя версия — 2.1.1.
Для запуска новой версии требуется полная перезагрузка Switch в Atmosphere. Обычный Core рассчитан на
инъекцию в приложение и перехваты графических API. Наш GLES-код находится в NRO
и вручную загруженных Android ELF, поэтому r31 передаёт телеметрию напрямую.
Менять флаги отладки форвардера или переустанавливать NSP для этого не требуется.

Протокол взят из официального тега 2.1.1:
[NxFpsSharedBlock](https://github.com/masagrator/SaltyNX/blob/2.1.1/saltysd_core/source/NX-FPS-Common.hpp),
[IPC-клиент](https://github.com/masagrator/SaltyNX/blob/2.1.1/saltysd_core/source/saltysd_ipc.cpp).
Клиент подключается к `SaltySD`: `InjectServ` принимает и сразу закрывает
соединение, команды моста там не обслуживаются. Использованный в r29 порт был неверным, но смены порта оказалось недостаточно:
в аппаратном тесте r30 соединение также вернуло `0x10801` ещё до IPC. Этот код
означает исчерпанный ресурс; конкретный бюджет должен проверяться, а не угадываться.
IPC 7 получает shared-memory handle, IPC 6 резервирует блок 310 байт. Сессия
закрывается после инициализации. При отсутствии сервиса/ошибке игра сохраняет
обычный вывод; активный чужой производитель NX-FPS не перезаписывается.

`nx_salty.c` получает timestamp настоящего EGL present из `nx_perf_present`.
Публикует MAGIC, API=EGL, средний FPS, последние десять интервалов в system ticks
и номер кадра. Пустые NVN counters не выдаются за измерения GPU.
Для FPSLocker читаются handheld/docked FPSlocked: поддержан программный лимит
15–60 FPS. Запрос выше 60 не снимает существующий Unity targetFrameRate=60.
Буферизация, ZeroSync, ReverseNX и игровые FPS-патчи этим мостом не реализуются.

Проверка на ПК: настоящий код статистики/ограничителя с управляемыми часами,
ABI-размер и offsets, отсутствие сервиса, точные 60 FPS, разные режимы и
недопустимый лимит. Нативная сборка проверяет IPC-вызовы по установленному libnx.
Дополнительный тест запускает настоящий nx_salty_init со стендом сервиса:
проверяет имя порта, PID, копию handle, reservation и обработку ошибок.
Работа IPC и отображение в оверлее на Switch ещё требуют проверки r31 после полной перезагрузки.

В журнале ожидается `[saltynx] direct NX-FPS bridge mapped ... ABI=310`.
`unavailable`/`bridge skipped` означают, что прямой мост не подключён.
Сравнить FPS/frametime в Status Monitor с `[perf]`; затем проверить cap 30 и 60.
SaltyNX не ускоряет игровую логику и не создаёт недостающие кадры.

Отключение прямого моста: `saltynx 0` в config.txt, default 1.
Сохранённые файлы настроек FPSLocker пока не загружаются мостом; cap меняется
через оверлей в текущем запуске. Лимит Unity остаётся 60.


В r31 при первом connect rc=0x10801 запрашиваются текущий и предельный SessionCount
для собственного процесса. Только при фактическом исчерпании небольшого бюджета
(до 128) запрашивается ещё 8 сессий; результат syscall записывается в журнал.
Если лимит не исчерпан, он не меняется. Не меняются лимиты памяти или потоков.
Другие причины нехватки ресурсов этим запросом не считаются устранёнными.

Неудачное подключение повторяется на успешном present раз в секунду, максимум
30 попыток, без sleep/retry-цикла в кадре. При успехе повторные подключения
прекращаются. Активный чужой producer остаётся нетронутым. По стадиям журнала
различаются connect, получение handle, map и reservation.

Официальный архив 2.1.3 проверен по GitHub SHA-256:
`9c575b3eee27ee9d760b575f57f6b44b9e971cea40afc68f8bd179b3eab48c24`.
Оригинальные sysmodule/Core/bootstrap/IPS записаны с резервной копией; личные
исключения, дополнительные плагины и настройки не удаляются. Одна установка
файлов не подтверждает отображение FPS в оверлее.
